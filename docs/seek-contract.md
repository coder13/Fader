# Seek preparation: qualification contract

Tracking: [DJ-039](https://github.com/coder13/Fader/issues/39). Status: software qualification complete within the declared measured and fallback scopes. Targets below were set before measurement. See the [qualification report](experiments/2026-11-04-cancellable-seeking.md) for measured results, and the [native report](experiments/2026-11-05-native-seek-export.md) for completed UI observations.

## Targets and measurement scope

For the current two-clip volume/HP/LP renderer on the development Apple Silicon Mac, target **warm p95 ≤150 ms** and **cold p95 ≤500 ms**, from accepted request to a ready playback engine. Report p50, p95, maximum and misses. Cold means a new engine/source reader, not an artificially purged OS disk cache. Fixtures include the two long overlapping WAVs from DJ-038 and CBR/VBR MP3 arrangements with distant/nonzero source positions. Import/validation/cache creation is measured separately and never hidden inside a warm seek result.

Compare nonzero-start master/cue PCM with uninterrupted sequential rendering, with an absolute tolerance of **1e-5 for the normalized synthetic fixtures**. Compare prepared volume/HP/LP values at the same tolerance. Explicitly test continuous ramps, held targets, bypass boundaries, delayed clip starts, source offsets/rates and changes immediately around the destination. Report errors rather than weakening the tolerance after measurement.

The reproducible probe uses 40 first-visit/immediate-repeat pairs in a coprime destination order. Both construct a fresh engine and decoder readers; “warm” means the just-read data is revisited. Import has already touched the original files, so even the cold measurement is not a physical disk cold-cache claim. Request-to-ready includes preparation-worker retirement and 1 ms completion polling; the native UI may add one 30 Hz timer tick. Timing does not run concurrently with builds or fixture encoding.

## Selected approach to test

Use at most **two seconds of project-frame preroll** for the existing finite volume smoother and simple stable one-pole HP/LP stages. Start those controls from their envelope values at the preroll origin and process the real source through the same engine until the destination. Retain exact-from-start preparation as the reference option. Processing from project zero, including ordinary full export, keeps its existing behavior. This bounded-preroll policy does not apply automatically to future stretchers, resonant effects, delay/reverb or third-party plugins; they need checkpoint/state/tail contracts of their own.

The pinned MP3 decoder's sequential-replay fallback is correct but is not a fast random-seek mechanism. Test a session-owned local PCM cache populated during the existing validation scan, so seeking preserves that decoder's exact sample domain without re-decoding every preceding frame. Bound aggregate decoded disk storage to **8 GiB per running process**, keep the existing bounded memory pages, and retain original-file identity checks. If the cache cannot be admitted or written, preserve readable-source support with an explicit slower preparation path; report that mode and any missed target. Cache paths are internal and never serialized into the set or written into the music library.

## Cancellation, ownership and UI

Carry one cancellation flag through preparation, decode readiness and worker reads. Observe it between bounded render/decode chunks. A superseding request cancels the active preparation and replaces one pending request; old completions may not start playback or mutate the project. Scope each request to a generation and immutable project snapshot.

No callback waits, allocations or ownership reclamation are introduced. Keep playback destruction and source-worker joins off interactive UI actions. Bound pending requests, completed results and retired engines; do not queue an unlimited job for each mouse movement. Show Preparing and a Cancel action, allow a new seek to replace the old destination, and preserve the latest project on source changes/close. OS reads already in flight can outlive cancellation, so storage lifetime must remain valid until those reads return.

Native UI inspection and delayed-worker lifetime tests are required in addition to timing and PCM comparisons. None of these measurements qualifies physical input/output latency.

## Implemented ownership and fallback

`PlaybackPreparation` owns one worker, one pending request and at most one playback engine. The UI borrows a ready engine until it detaches its audio callback and invalidates the request. The worker destroys that engine and joins its decoder workers before constructing another. Pending requests replace each other while retirement completes. The usual 32 MiB maximum PCM page allocation is therefore not multiplied by a backlog of seeks; the two-clip measurement allocates 1 MiB of pages. Immutable plan snapshots share source/cache ownership and are reused for repeated seeks until an edit invalidates them. No worker posts a completion into a deleted window: the UI polls only the latest generation. A request may take longer if an old OS read cannot yet return, while Cancel/New/Open can invalidate it immediately.

The native UI displays **Preparing** with **Cancel** on the Play button. Clicking the ruler while playing/preparing replaces the destination and continues ordinary playback; seeking during a capture cancels/stops that take. Editing, New, Open, and close invalidate preparation. Capture is armed only after the latest engine is accepted. Application shutdown detaches/destroys the window before joining the preparation worker. General import/export/library jobs keep their existing busy-operation rules; this issue does not claim cancellable full-library scanning or export.

Cache construction for JUCE MP3 and CoreAudio-decoded sources runs during import, with stereo native float frames and bounded 8192-frame scratch blocks. Readers retain the cache while decoding; original size/mtime is checked before/after each worker read and full SHA-256 identity is checked on import/reopen. Disk-cache failures release the reservation and retain the selected reader’s uncached decoding. The preparation status explicitly says an uncached source may seek slowly, including the native CoreAudio path. The JUCE sequential fallback is cancellable between decode chunks. CoreAudio keeps its native seek implementation when uncached. Both missed the warm target on the declared long MP3 fixtures, and CoreAudio/JUCE may expose different priming/padding lengths; the cache preserves whichever decoder was selected rather than forcing a switch.

On POSIX, the private temporary file is created in the user temp directory and immediately unlinked; the open descriptor retains storage until its last owner closes ([unlink semantics](https://man7.org/linux/man-pages/man2/unlink.2.html)). Windows uses a non-inherited `CreateFileW` handle with `FILE_FLAG_DELETE_ON_CLOSE` ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)), then transfers ownership to the CRT stream ([ownership rules](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/open-osfhandle?view=msvc-170)). Cache paths never enter project files. Only Mac execution is measured here; the Windows implementation needs its platform qualification.
