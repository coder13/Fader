# Cancellable seeking qualification

Issue: [DJ-039](https://github.com/coder13/Fader/issues/39). Status: implementation, local correctness/lifetime tests and timing measurements passed for the cached path. Clean Linux/macOS CI passed; native visual verification remains pending. Uncached long MP3 misses at least the warm interactive target on both decoder paths; that fallback stays explicitly slower and cancellable. No audio device/controller is used in these measurements.

## Configuration and targets

Local Apple Silicon arm64, Darwin 25.6.0/macOS 26.6.2, AppleClang 21.0.0.21000334, CMake 4.4.4, Release/C++20; JUCE 9.0.5 at `d60b7a78030661574a615b586d9325ba7a7fa7dd`. Implementation: `c9dba8c0407eccbf7dfd93998d197f40127a87db`. Measurements used the staged Release implementation committed there; the final pre-commit changes were comments and the fixture recipe, with no renderer/cache/preparation behavior changes. The new concurrency tests also passed in a standalone Apple ThreadSanitizer build. Follow-up `05e21112f7cfb424c51cd3c9ad12fda309c89230` preserves/caches the native CoreAudio PCM domain; final `f7ecbae3fd156c519f2ea1e9f9d00c3fed76933c` adds explicit uncached-path reporting and probe access without changing rendering or cache samples. The CoreAudio measurements below use the follow-up implementation.

The [contract](../seek-contract.md) set warm p95 ≤150 ms, cold p95 ≤500 ms and absolute PCM/control error ≤1e-5 before measurement (initial targets commit `802ace0`). “Cold” here means a first visit to a destination using fresh engine/decoder readers, after import; “warm” means its immediate repeat, also using fresh readers. The OS file cache is **not purged**. This is not storage-cold latency, device latency or a platform-wide performance promise.

The probe uses 40 first-visit/repeat pairs, visiting destinations in a fixed coprime order. Timing begins at the request and ends when polling accepts the current generation; it includes retirement of an earlier engine. Completion is polled every 1 ms. The native UI polls at 30 Hz and can add a timer tick. Import, validation, PCM-cache creation, first UI snapshot copying and initial device setup are outside these seek timing figures. No local build, sanitizer run or encoder ran concurrently with timing.

## Fixtures and reproduction

WAV: the two 2 h 15 m sparse stereo PCM16/48 kHz sources from [DJ-038](2026-11-04-bounded-streaming.md), with B starting at 30 minutes. Each clip skips two source seconds, yielding a 2 h 44 m 58 s arrangement. Seek positions span the overlap. Sparse silence/bursts do not represent worst-case continuous music or storage.

MP3: two 30-minute synthetic rhythm sources, generated by looping the DJ-038 three-minute WAVs ten times: 48 kHz/320 kbit/s CBR and 44.1 kHz/quality-2 VBR using libmp3lame/FFmpeg 7.1. Clips start at two hours and two hours plus 30 seconds, with two-second source offsets. The arrangement is 2 h 30 m 28.046 s with the JUCE MP3 reader and 2 h 30 m 28 s with CoreAudio; its first two hours are empty, and seeks span the active overlap. These are long source-position seeks, not evidence of two hours of continuous compressed playback.

## Correctness, cancellation and bounds

- `seeking` compares two 20-second two-clip projects against uninterrupted rendering at 11 destinations each. It covers rates 8–384 kHz, speeds 0.25–4, delayed starts, nonzero source offsets, ramps, holds and filter bypass boundaries. Maximum absolute master/cue PCM and prepared volume/HP/LP errors were both **0**, inside the 1e-5 contract. This validates the current simple filters on the declared normalized fixtures; it is not a universal bit-exact guarantee for future effects.
- A blocked cooperative decoder exits when preparation is cancelled. A separate factory deliberately ignores cancellation and returns a late success: 1,000 superseding requests, cancellation and source replacement still publish only the latest project/position. Only two builds run in that fixture (the initial blocked job and the final request).
- Closing during a delayed failure yields no completion. A decoder destructor deliberately stalls; Cancel and a new request return without waiting, and the next engine is built only after retirement releases. All engine destruction/decoder joins stay on the preparation worker. The test guards these control operations with a one-second CI timeout, not a claim of measured sub-millisecond UI latency.
- A targeted ThreadSanitizer build of Engine, Streaming, Playback, PlaybackPreparation, SeekTests and PreparationTests passes without a race report. This is not a whole-app sanitizer result.
- Native cache tests verify the 8 GiB aggregate admission/release limit without writing a huge test file, two concurrent readers at different positions, cancellation, overflow-safe offsets, source modification/deletion rejection and cached/uncached VBR parity. Session cache files are not serialized.
- Full sequential comparison of both 30-minute MP3s with an independent decoder, followed by 14 forward/backward/tail windows each, reports **0** sequential and seek sample error for cached JUCE and cached/uncached CoreAudio PCM separately. This does not assert that the two decoders produce identical output to each other. Local native CTest passes **5/5**, including callback allocation regression fixtures.

## Remaining verification and limits

Initial [CI on c9dba8c](https://github.com/coder13/Fader/actions/runs/41985356675) passed Linux and four Mac core suites but caught a real native-decoder path omission: the MP3 cache was only enabled for JUCE's reader. Reproducing outside the local sandbox confirmed CoreAudio was chosen instead. The fix caches either reader's own PCM, preserving existing decoder selection. Local native tests then pass 5/5 both with and without native codec access; the final reporting change also passes the native media suite. Final [clean CI on f7ecbae](https://github.com/coder13/Fader/actions/runs/41987112951) passes Linux 4/4 and macOS 5/5, including app signature verification. Downloaded artifacts match that exact source and the JUCE pin, with fixtures OFF, zero failures/errors/skips, zero seek PCM/control error and the allocation/cancellation/retirement success markers. Linux is GNU 13.3/CMake 3.31.6/x86_64; macOS is AppleClang 17.0.0.17000013/CMake 4.4.4/arm64 Darwin 24.6.0. Native inspection of Preparing/Cancel, superseding ruler seeks, editing/source replacement and close is pending because the Mac locked again after the completed DJ-038 preview inspection. The existing preview and user set have been left running unchanged; the seek build has not replaced it. Preserve any new edits before that update, keep the same preview identity, and share a synthetic screenshot after verification.

CoreAudio reports exactly 1,800 seconds for these MP3s; JUCE reports 1,800.024/1,800.046 seconds due to its decoder sample domain. The eight-second VBR likewise reports 352,800 versus 354,816 frames at 44.1 kHz. These pre-existing decoder differences must be captured by the asset/render identity policy in [#11](https://github.com/coder13/Fader/issues/11) and platform/media qualification in [#35](https://github.com/coder13/Fader/issues/35)/[#41](https://github.com/coder13/Fader/issues/41). This change deliberately does not switch a user's decoder or claim cross-decoder/cross-platform render identity.

The two-second filter reconstruction policy is specific to the current smoother and stable one-pole HP/LP stages. Future stretch, delay/reverb, resonance and plugins require their own state/checkpoint/tail policies. OS reads can outlive cancellation; the worker retains storage until they return, so a later seek may wait even though the UI can invalidate it. General import/export/library cancellation, large-session UI scalability, continuous load, Windows native execution and hardware latency remain separate work.
